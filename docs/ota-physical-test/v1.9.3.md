## Two-Phase Execution Order

The authorized release (tag `v1.9.3`) is created by the release pipeline
AFTER hardware acceptance passes. Physical OTA evidence therefore runs in
two phases:

- **Phase A — pre-publish fail-closed regression (can run BEFORE the release
  exists)**: verify the PWA refuses to flash anything when the authorized
  tag is not published yet and GitHub `latest` is still v1.8.0.
- **Phase B — full 16-criteria protocol (runs AFTER the v1.9.3 release is
  published)**: the happy-path production OTA + rollback test.

---

## Checklist (16 Criteria)

### Criterion 1: Device running firmware before OTA

- [ ] Open PWA in browser, navigate to OTA view
- [ ] Verify "Current Version" shows the pre-OTA version (e.g., `1.8.0` or `1.9.2`)
- [ ] Record `preOtaVersion` in evidence JSON
- [ ] Record `preOtaUptimeSec` (from device diagnostics or PWA status)

**Expected**: Device is accessible via PWA, running a version < 1.9.3.

### Criterion 2: PWA resolves the AUTHORIZED release (by immutable tag)

- [ ] In OTA view, click "Fetch Authorized Release (v1.9.3)" in the
  "Push Canonical Release" card
- [ ] **Phase A (pre-publish regression — P0 PWA-01)**: while tag `v1.9.3` is
  NOT yet published and `releases/latest` is still `v1.8.0`, the PWA must:
  - [ ] show a fail-closed message (authorized release v1.9.3 not published)
  - [ ] expose the current `latest` tag (v1.8.0) in the message
  - [ ] NOT offer any binary to push (no fallback to latest)
  - [ ] record `pwaFailClosedPrePublish: true` in evidence JSON
- [ ] **Phase B (post-publish)**: after the v1.9.3 release exists, the PWA
  resolves the release BY TAG and displays: version, build ID, SHA-256,
  git commit, release URL
- [ ] If GitHub `latest` != `v1.9.3` (stale latest), the PWA shows the
  "latest ≠ authorized" warning badge and still pins to v1.9.3
- [ ] Record `pwaLatestMismatchWarningShown` in evidence JSON (true when the
  badge was shown; false when latest == v1.9.3)

**Expected**: Canonical identity comes from the pinned tag, never from the
mutable `latest` pointer.

### Criterion 3: PWA resolves version + SHA correctly

- [ ] Verify displayed version = `1.9.3`
- [ ] Verify displayed SHA-256 matches `modular-release.json` `firmwareSha256`
- [ ] Verify displayed git commit matches the release commit (lineage `cadc396…`)
- [ ] Record `pwaCanonicalVersion` and `pwaCanonicalSha256` in evidence JSON

**Expected**: All three fields match the published release candidate.

### Criterion 4: PWA triggers OTA

- [ ] Click "Push v1.9.3 to Device" button
- [ ] PWA downloads `modular-firmware.bin` from the authorized release assets
- [ ] PWA downloads `modular-firmware.bin.sig` (128 hex chars) from the
  authorized release assets
- [ ] PWA computes SHA-256 of downloaded binary using `crypto.subtle.digest`
- [ ] PWA verifies computed SHA matches the authorized release SHA
- [ ] PWA validates delivery metadata BEFORE upload (signature = 128 hex,
  SHA = 64 hex, version = strict SemVer)
- [ ] PWA uploads binary to device `POST /api/ota` with headers:
  - `X-Expected-SHA256: <authorized release sha256>`
  - `X-Signature: <release signature>`
  - `X-Firmware-Version: 1.9.3`
- [ ] Record `pwaCanonicalShaMatchedClient: true` in evidence JSON

**Expected**: Upload progress bar advances to 100%. No SHA mismatch error.

### Criterion 5: Device receives artifact

- [ ] Device's `OtaHandlers.cpp` `UPLOAD_FILE_START` handler fires
- [ ] Auth + CSRF check passes (JWT cookie + X-CSRF-Token)
- [ ] Headers `X-Expected-SHA256`, `X-Signature`, `X-Firmware-Version` are read
- [ ] `PRODUCTION_BUILD` signature check passes (signature header is present)
- [ ] `OtaManager::beginUpload()` initializes streaming SHA-256 + flash write

**Expected**: Device accepts the upload start. No 500 error.

### Criterion 6: Signature verification passed

- [ ] Device's `OtaManager::finalizeUpload()` runs `_validateEd25519()`
- [ ] Ed25519 signature is verified against the 32-byte raw SHA-256 digest
- [ ] Verification uses `OTA_ED25519_PUBLIC_KEY_HEX` compiled into firmware
- [ ] `Utils::ed25519VerifyHash()` returns true

**Expected**: No `VERIFICATION_FAILED` lifecycle event. Device does not reject the binary.

### Criterion 7: SHA-256 verification passed

- [ ] Device's `OtaManager::finalizeUpload()` runs `_validateSha256()`
- [ ] Streamed SHA-256 (computed during `feedChunk()`) matches `X-Expected-SHA256` header
- [ ] Constant-time comparison via `Utils::constantTimeMemEquals()`
- [ ] SHA also matches the hash used for Ed25519 signature verification

**Expected**: No `VERIFICATION_FAILED` lifecycle event. `Update.end(true)` succeeds.

### Criterion 8: Download complete (no partial/corrupt image)

- [ ] All bytes are written to flash via `Update.write()`
- [ ] `Update.end(true)` returns true (flash write verified)
- [ ] No `DOWNLOAD_FAILED` or flash write error in device logs
- [ ] Device sends HTTP 200 `"OTA complete — reboot pending"`
- [ ] Record `uploadDurationSec` and `uploadBytes` in evidence JSON

**Expected**: Device responds with 200, then reboots after 500ms delay.

### Criterion 9: Boot/reboot succeeded

- [ ] Device reboots into the new OTA partition (`ESP_OTA_IMG_PENDING_VERIFY`)
- [ ] Boot completes within 5 seconds
- [ ] WiFi reconnects within 30 seconds
- [ ] NTP syncs within 60 seconds
- [ ] MQTT reconnects (TLS)
- [ ] Boot health check starts (60-second stable window)

**Expected**: Device becomes accessible again via PWA after reboot.

### Criterion 10: Device running 1.9.3

*(check key `deviceRunning180` is a legacy v1.8.0 schema label — the value
verified here is version 1.9.3, recorded in `observed.postOtaVersion`)*

- [ ] PWA version strip shows `currentVersion: 1.9.3`
- [ ] `GET /api/version` returns `firmwareVersion: "1.9.3"`
- [ ] Record `postOtaVersion: "1.9.3"` in evidence JSON

**Expected**: Device reports the new version.

### Criterion 11: Device reports correct identity

- [ ] `GET /api/version` returns:
  - `firmwareVersion: "1.9.3"`
  - `buildProfile: "PRODUCTION"`
  - `buildDate` = the deterministic SOURCE_DATE_EPOCH-derived date
    (v1.9.3 reproducible build: `__DATE__/__TIME__` replaced by the
    source-commit timestamp — two builds of the same commit embed the
    SAME buildDate)
- [ ] Telemetry payload includes `firmwareVersion: "1.9.3"`
- [ ] Record `postOtaBuildProfile` in evidence JSON

**Expected**: All version fields are consistent and correct.

### Criterion 12: Relay state safe after reboot

- [ ] During reboot: relay de-energizes (hardware active-LOW, Hi-Z = ISOLATED)
- [ ] After reboot: system starts in `EMERGENCY`/`BOOT` state (relay ISOLATED)
- [ ] No relay channel is ON without explicit operator ARM command
- [ ] If 8-channel relay module connected: all 8 channels OFF at boot
- [ ] Record `relayStateAfterReboot` in evidence JSON (e.g., "all OFF, ISOLATED")

**Expected**: Relay is in safe state. No glitch ON. System requires explicit ARM.

### Criterion 13: Sensors/alarms normal

- [ ] INA219 voltage reading within ±0.2V of expected
- [ ] INA219 current reading within expected band for the test load
- [ ] Temperature reading within ±2°C of expected
- [ ] No new alarms triggered by the OTA process
- [ ] Existing alarms (if any) are preserved or cleared per normal logic
- [ ] Record `sensorReadingsNormal: true` and `alarmsActiveAfterOta` in evidence JSON

**Expected**: Telemetry is normal (v1.9.3 INA219 measurement chain intact
after OTA). No OTA-induced alarms.

### Criterion 14: OTA transaction reached terminal state

- [ ] After 60-second stable window, `markBootHealthyIfPending()` fires
- [ ] `esp_ota_mark_app_valid_cancel_rollback()` called
- [ ] `ACTIVATED` lifecycle event emitted to MQTT topic `plts/<deviceId>/ota/event`
- [ ] GAS `OTA_LOG` sheet records the `ACTIVATED` event
- [ ] PWA OTA history table shows the update with status `success` and the
  source badge "Authoritative — GAS OTA_LOG"
- [ ] Record `otaHistoryEntryStatus: "success"` and `deviceLifecycleEvents` array in evidence JSON

**Expected**: OTA reaches `ACTIVATED` terminal state. Boot image is confirmed.

### Criterion 15: Backend/PWA see same final state

- [ ] PWA `GET /api/version` shows `1.9.3`
- [ ] PWA OTA history shows `ACTIVATED` / `success`
- [ ] GAS OTA_LOG sheet shows `ACTIVATED` with correct version + timestamp
- [ ] Device telemetry (MQTT) shows `firmwareVersion: 1.9.3`
- [ ] All three sources (device REST, GAS log, MQTT telemetry) agree on version + status

**Expected**: Consistent state across all observation points.

### Criterion 16: Rollback/recovery works (failure case test)

This criterion tests the rollback path. It should be performed AFTER criteria 1-15 pass, on a separate test cycle:

- [ ] **Option A (boot-health failure)**: Upload a firmware that panics during boot
  - [ ] Device fails boot health check within 60 seconds
  - [ ] Bootloader auto-reverts to the previous partition
  - [ ] `ROLLBACK` lifecycle event emitted with correct failed version
  - [ ] Device boots into the previous firmware and is accessible
  - [ ] PWA shows the rolled-back-to version

- [ ] **Option B (NVS counter)**: Upload a firmware that fails boot 3 times
  - [ ] After 3rd failed boot, `triggerRollback()` fires
  - [ ] `esp_ota_mark_app_invalid_rollback_and_reboot()` called
  - [ ] `ROLLBACK` lifecycle event emitted
  - [ ] Device boots into the previous firmware

- [ ] Record `rollbackTestResult` in evidence JSON (e.g., "Option A: PASS — bootloader auto-revert worked, ROLLBACK event emitted, device recovered")

**Expected**: Rollback mechanism works. Device recovers to the previous working firmware.
